Frequently asked questions

These answers use the desktop client commands. On Android the same concepts apply through the app's screens — the Android-specific notes are called out where they differ. If you are new, read the getting started guide first.

Three words worth keeping straight: a device is one computer or phone enrolled to your account (it holds its own key); a database is a vault on the server (one shared UUID, no matter how many devices use it); a binding is the local link on one device between a .kdbx file and a server database. Most questions below are really about one of these three.

Devices & tokens

How do I get a token for a new device so it joins the others?

Each device needs its own one-time enrollment token — tokens are single-use, so you cannot reuse the one from your first device. Ask your administrator to issue a fresh one:

# Administrator runs:
./keepass-deltasync admin user-enrollment <your-username>
# → prints a new enrollment token

Then on the new device, enroll with that token:

./keepass-deltasync enroll --server https://deltasync.org <new-token>

Enrolling links the device to your account. It does not yet point at any vault — to actually share data with your other devices you then bind the device to the existing database (see “How do I bind a device to an existing DeltaSync database?” below). On Android, do the same on the main screen: scan the QR code the admin panel shows, or enter the server URL and the new enrollment token by hand.

How do I see how many devices are connected to my sync?

Run devices — it lists every device enrolled to your account, with the one you are on marked with an asterisk:

./keepass-deltasync devices
#    NAME        ID        ENROLLED     LAST SEEN
# *  laptop      ab12…     2026-05-27   2026-06-09
#    work-pc     cd34…     2026-05-30   2026-06-08
#    phone       ef56…     2026-06-01   2026-06-09

LAST SEEN tells you when each device last synced — handy for spotting a device you forgot about. Administrators can also see a device count per user with admin user-list.

How do I remove a device I no longer use?

To stop a database from syncing on a device you still control, run forget on that device (see below). To revoke a device entirely — for example a lost or stolen laptop or phone — that is an administrator action; ask your admin to remove it (a full account reset via admin user-delete CASCADE-removes every device, but that also deletes your databases, so it is only for decommissioning the account). If a device may be compromised, also change your KeePass master password afterwards.

Bindings

How do I bind a device to an existing DeltaSync database?

This is the normal “second device” flow: you already sync a vault on one device and want another device to share the same data. First find the database’s UUID:

./keepass-deltasync databases
# NAME          ID                                    ...
# mypasswords   3f2b9c1a-…-…-…-…                      role=owner

Then bind a local .kdbx file on the new device to that UUID instead of creating a brand-new vault:

./keepass-deltasync init mypasswords ~/keepass/my.kdbx --bind <UUID>
./keepass-deltasync sync mypasswords

The local file can even be an empty/new .kdbx with the right master password — the first sync pulls the server entries into it. On Android, pick your .kdbx with the file picker and match it to the database shown from the server.

How do I delete a previous binding?

Use forget on the device whose binding you want to drop:

./keepass-deltasync forget mypasswords

This removes only the local link in that device’s config. The server database and the .kdbx file are left completely untouched — your passwords are not deleted, and your other devices keep syncing. It is exactly what you want after an account switch where an old binding went stale, or when you simply want to stop syncing a vault from this one device. List your current bindings any time with databases. To pick the database up again later, just init … --bind <UUID> as above.

How do I delete a whole database from the server (e.g. a leftover duplicate)?

This is different from forget. forget only drops the local binding; the server vault lives on. If databases shows a row marked ? / (not bound locally) that you want gone for good — typically a duplicate created by accident — you need to delete the server database itself.

Only the owner can do this. Use the delete-database command, which takes either a local name or a raw UUID — pass the UUID for an unbound duplicate that has no local name:

# Look up the UUID first
./keepass-deltasync databases

# Delete by UUID (or by local name, if it is bound)
./keepass-deltasync delete-database <UUID>

It shows the database's real server name, asks you to type yes to confirm, then deletes it. Add --yes to skip the prompt. If the database was also bound locally, the binding is removed too (your .kdbx file is left untouched). Re-run databases to confirm.

This is permanent. Deleting a database CASCADE-removes all of its entries and version history on the server. Double-check you are passing the UUID of the unwanted row — the one marked ? — and not the * database you actually sync.

The stored master password

My new password is in the wallet, but I changed the connection — how do I make it work again?

The daemon caches your master password in the OS “wallet” (Windows Credential Manager / macOS Keychain / Linux Secret Service) per database, keyed by the database UUID. When you change the connection — re-binding to a different vault, or changing the vault’s master password — the wallet can still hold the old entry, so the daemon keeps trying the stale password and sync fails.

The fix is to clear the stale entry and let the daemon store the new one:

  1. Stop the daemon if it is running.
  2. Remove the saved credential from the OS wallet. On Windows: Control Panel → Credential Manager → Windows Credentials, find the entries named keepass-deltasync and remove them. On macOS: open Keychain Access, search keepass-deltasync, delete. On Linux: use Seahorse (“Passwords and Keys”) and delete the keepass-deltasync items.
  3. Re-run the daemon so it prompts once for the new password and saves it again: 
    ./keepass-deltasync daemon --store-keyring

If you simply forget and re-init --bind to a new vault, the new database has a new UUID, so the daemon prompts fresh on its own — no manual cleanup needed (the old wallet entry just becomes harmless dead weight you can delete at leisure).

On Android the master password lives encrypted in the Android Keystore. To refresh it, turn “Auto-sync in the background” off and back on — you confirm with biometrics and re-enter the current master password, which replaces the stored one.

I changed my KeePass master password — what do I do on my other devices?

The master password is never stored on the server, so each device that had it cached needs the new one. On every other device, refresh the wallet entry exactly as in the previous answer (clear the old credential, then daemon --store-keyring), or on Android toggle auto-sync off and on. Until you do, that device will fail to decrypt and sync.

Sharing & recovery

How do I share a database with another user?

If you own the database:

./keepass-deltasync share mypasswords alice    # grant access
./keepass-deltasync shares mypasswords         # list members
./keepass-deltasync unshare mypasswords alice  # remove a member

The recipient bootstraps their own local copy with init-shared and chooses their own local password — it need not match yours. Sharing is asymmetrically encrypted: only the recipient’s device can unwrap the key. See the getting started guide for the Share screen on Android, and the architecture page for the trust model.

I deleted an entry by accident — can I get it back?

The server keeps up to three previous versions of every entry. List them and roll back:

./keepass-deltasync versions mypasswords <entry-uuid>
./keepass-deltasync restore mypasswords <entry-uuid> 1

Find the entry UUID from KeePassXC, or from the versions/log output.

Where is my configuration stored?

The client keeps its bindings and device token in config.toml:

  • Windows: %APPDATA%\keepass-deltasync\config.toml
  • macOS: ~/Library/Application Support/keepass-deltasync/config.toml
  • Linux: ~/.config/keepass-deltasync/config.toml

Your master password is not in there — it lives only in the OS wallet (if you opted into --store-keyring) or in your head.

The desktop app & Firefox

Do I have to use the command line?

No. The desktop app covers the everyday work in a window: a wizard for enrollment and your first database, then a dashboard for syncing one database or all of them, seeing your devices and activity, and switching background sync on at login.

It is deliberately a thin shell around the same client — it holds no encryption, no server logic and no configuration of its own, it just runs the client and shows you the output. So the two are interchangeable: enroll in the app and the command line sees it, and the other way round. A handful of things still only exist as commands, notably sharing (share, init-shared) and version history (versions, restore).

Where do I get the Windows installer, and does it need administrator rights?

KeePass-Delta-Sync-Setup-<version>.exe is on the releases page. It installs for your user only and never asks for administrator rights — which is consistent with the rest of DeltaSync, since background sync at login is also set up inside your own account.

It contains both the desktop app and the command-line client, and puts them in the same folder on purpose: that is how the app finds the client, with no PATH to configure. There is an optional component with a source archive of both, switched off by default.

Can I use the Firefox extension without running a DeltaSync server?

Yes. A search never touches the network — the native messaging host reads your local .kdbx through keepassxc-cli and answers from that alone. If all you want is to find the right page fast, you can ignore the sync half of the project entirely.

Registering the database has its own command for exactly this case — init would require enrollment, this does not:

keepass-deltasync add-local private ~/keepass/my.kdbx
keepass-deltasync install-browser-host

Then load the extension, and that is the whole setup. Add --save-password to the first command to keep the master password in your operating system's keyring; without it the popup asks on the first search and the host holds it in memory only, wiping it when the idle lock expires or you press Lock. Step-by-step instructions are on the Firefox page.

Where do I get the extension?

From addons.mozilla.org, signed and reviewed like any other add-on. It needs the keepass-deltasync client installed and registered first — the setup page is three steps.

Two things are worth knowing. The extension requests no host permissions at all, so it cannot read the pages you visit. And it never receives a password: the host hands it titles, addresses and group names, and nothing else — an allow-list enforced on the host's side, so a bug in the extension cannot widen it.
