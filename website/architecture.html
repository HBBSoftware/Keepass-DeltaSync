Architecture

DeltaSync is built around the principle that the server should not be able to access your passwords — even if it is compromised. We achieve this by doing all encryption on the client and only storing opaque blobs on the server. Here is how it fits together.

The same crypto core runs on every client: the desktop client (Go) and the Android app (the identical Go code, compiled into the app via gomobile) derive keys and encrypt entries the same way, so a blob written by one is byte-for-byte readable by the other. Entries are encrypted in a platform-independent canonical format rather than a raw KeePass XML fragment, which is what makes that cross-platform compatibility exact.

1. Crypto stack: from master password to entry blob

When you first register a database, the client runs this chain of derivations on your master password:

Diagram 1: Key derivation and entry encryption. Client-side only; the server sees only the golden blob.

Why this chain:

  • Argon2id protects against brute-force on the master password — even a "weak" password like correct horse battery staple becomes expensive to guess (~200 ms per attempt, 64 MiB RAM).
  • HKDF-SHA256 gives a deterministic, independent key per use case — so we can use the same master_key for both entry encryption and future use cases without cross-contamination.
  • XChaCha20-Poly1305 is authenticated encryption — the server cannot tamper with blobs without the client noticing (MAC failure).
  • Random nonce per entry in a 2^192 space makes nonce reuse practically impossible.

2. Single-user sync: what happens during push and pull

The daemon runs in the background and reacts to two triggers: fsnotify (you saved in KeePassXC) and polling (periodic check for changes from other devices).

Diagram 2: Bidirectional sync. Both devices have the same master_key (derived from the same password); the server only sees encrypted blobs.

3. Multi-user sharing: how master_key reaches Bob

For Bob to decrypt entries in a database Alice shares with him, he needs her master_key. That is the core challenge — we cannot just send it in cleartext. The solution is sealed-box wrapping: Alice encrypts master_key with Bob's device public key, sends the opaque blob to the server, and Bob's device decrypts locally with his private key.

Diagram 3: Sealed-box wrapping. Alice encrypts master_key to Bob's device public key. The server can see who has access, but cannot open the wrap.

4. What the server sees vs. doesn't see

Element Server sees Server does NOT see
Entry content Title, username, password, notes, URL, attachments
Entry metadata UUID, mtime, deleted flag, server_seq, version count
Database info Name (Alice's choice), creation, members How many entries, their structure, group hierarchy
User Username, display_name, devices, last_seen Master password, master_key, device private keys
Sharing Who shares with whom, wrapped_master_key (opaque) The wrapped master_key — only the recipient can open it
Audit log IP, user-agent, endpoint, timestamp per request Request body content beyond the metadata above
Forensic re-opening is fundamentally unavoidable: if Alice shares a database with Bob and later regrets it, she can remove his future access via unshare, but Bob still has whatever blob data he managed to download as well as his copy of master_key. Sharing is a trust action — not a revocable access control.

5. Concurrent writes — what if two devices edit at the same time?

Server-side, all entry writes are serialized via a row lock on database_seq. Two concurrent PUTs get distinct server_seq values; the highest wins as the "current version".

Client-side uses last-writer-wins via the entry's internal LastModificationTime. KeePassXC's merge is field-level, so Alice (password edit) + Bob (username edit) both keep their changes. Conflicting edits on the same field lose one.
